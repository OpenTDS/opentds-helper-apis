Helper endpoints for the hard parts of end-to-end testing

Catch the email an application sends, answer its MFA prompt, share test data between virtual users, prove a webhook fired, and gate a build on response times. Every call is a plain HTTPS GET, so a test framework, Postman, LoadRunner, curl or an AI coding assistant can use it with nothing but a URL.

How it works

Every action has the same shape:

{BASE_URL}/<service>/<action>?param=value

Try one now — it returns five random codes you can use to keep your test run separate from everyone else's:

{BASE_URL}/lists/codes

The rules every service follows

RuleWhat it means
GET everywhereEvery action answers GET. The few that take a file or message body also accept POST.
key is your namespaceData lives under a key you choose. Nothing needs creating first. Use a fresh random key for each test run so runs never collide.
Same verbs, same meaningpush appends, pop takes the next item, get reads one, set writes one, list reads many, reset rewinds, clear deletes.
wait instead of pollingCalls that wait for something (an email, a webhook, a lock) take wait= seconds, up to 20, and return the moment it happens.
Empty is not an errorAn empty queue returns HTTP 200 with "exhausted": true, so load-test tools don't count it as a failure.
Predictable errorsEvery error is {"error": "…", "status": 400}. Parameter names are case-insensitive.
No sign-upThere are no accounts or API keys. That also means anyone who knows a key can read its data — see acceptable use.

Services

Each card lists the service's actions. Full parameters and example responses are in the OpenAPI spec (3.2.1; 3.0.3 copy for tools that do not read 3.2 yet) and the guide.

lists

Keyed test-data queues shared by every virtual user: push/pop/random records, bulk CSV/JSON import (atomic replace), run-scoped variables, atomic counters, and a cleanup register for records a test created.

  • pushAppend a record to a key's queue
  • popTake the next record (each record is handed out once)
  • cyclepopTake the next record, starting again at record 1 after the last (pop that never runs out)
  • randomA random record, without consuming it
  • listRead the records of a key (paged for large keys)
  • resetRewind the pop pointer to record 1
  • clearDelete every record of a key
  • codesRandom uppercase alphanumeric codes (3, 4, 6, 8 and 10 characters)
  • vars/setSave a run-scoped variable under a key
  • vars/getRead a variable, optionally waiting for it to be set or to equal a value
  • vars/listList every variable of a key
  • counters/addAdvance a counter atomically
  • counters/getRead a counter without changing it
  • cleanup/pushRegister a record that will need removing
  • cleanup/popHand back the next record to remove
  • cleanup/listThe cleanup audit trail
  • uploadDrag-and-drop CSV/JSON loader (HTML page)
  • upload/urlPresigned S3 POST for a CSV/JSON file of up to 50 MB
  • importReplace a key's records from an uploaded file (ref)
  • import/statusProgress or result of an import

names

Regional personas for test data: a female and a male name sharing a surname, with ASCII-folded forms.

  • getA female and a male persona for a region
  • regionsList the available regions and their list sizes

mail

Inbound mail catcher (any address at the mail domain, popped per address), outbound send through SES with generated, saved or received attachments, and an attachment store with text search inside PDF, Office and text files.

  • popTake the next captured email for an address
  • resetRewind an address's pointer to its first message
  • clearDelete every captured email for an address
  • sendSend an email (query-string form)
  • attachments/saveSave a received attachment under a key (promote)
  • attachments/getFetch a saved or received attachment
  • attachments/deleteDelete a saved attachment
  • attachments/findSearch inside an attachment without downloading it
  • attachments/textThe text that attachments/find searches, page by page
  • attachments/compareIs this the same document? Compare two attachments
  • attachments/uploadBrowser page for uploading saved attachments
  • attachments/upload/urlPresigned S3 POST for uploading a large saved attachment

sms

Text messages: real texts caught by registered capture handsets (device-key protected), real sends to those handsets, and simulated texts to any other number.

  • receiveStore a text caught by a capture handset (device key required)
  • getNewest text message for a number
  • listEvery text message received in the last N seconds
  • sendSend a REAL text to a registered handset
  • mocksendSimulate a text message to any unregistered number

totp

TOTP secret store and RFC 6238 code generation for MFA-protected test accounts.

  • setStore a TOTP secret for a user
  • getGet the current, next and previous TOTP codes

webhook

Capture inbound webhooks from a system under test and read them back.

  • receiveCapture an inbound webhook (any method)
  • listList captured webhooks for a key (newest first)
  • clearDelete all captured webhooks for a key

lock

Short-lived (60 s, no renew) mutual exclusion between concurrent test scripts that share one resource.

  • acquireTake a short-lived lock on a shared resource
  • releaseRelease a lock you hold

qr

QR codes from text, as JSON (PNG as base64 and a data: URI), SVG, or a self-contained HTML page.

  • getEncode text as a QR code (JSON, SVG or HTML page)

perf

Record performance data points from test scripts and read back exact counts, means and bounds, histogram percentiles (~2% relative accuracy), per-minute time series and pass/fail gates.

  • addRecord one or more performance data points
  • statsSummary statistics for a key
  • seriesBucketed time series for a key
  • assertPass/fail performance gate
  • keysList the keys that have recorded results
  • clearDelete everything recorded for a key
  • exportExport the individual points for a key

voice

Spoken utterances for testing voice interfaces: text with [tags] for emotion, pace and pauses becomes audio, stored by content so every request can be replayed byte for byte.

  • saySay text: text (with [tags]) to audio, stored by content
  • getStored audio by ref or key (replay; nothing is synthesised)
  • saveKeep a generated utterance under a key (pin)
  • deleteDelete saved audio
  • voicesThe voices, and what each engine can render
  • tagsThe [tag] vocabulary and how each engine renders it

A worked example: sign-up with email verification and MFA

The flow most test suites find hardest to automate, end to end:

  1. Get a run key: {BASE_URL}/lists/codes → use rand10, e.g. 7Q2K9ZX4M1.
  2. Invent a person: {BASE_URL}/names/get?region=AU&seed=7Q2K9ZX4M1.
  3. Sign up in the application under test with the address signup-7q2k9zx4m1@{MAIL_DOMAIN}.
  4. Wait for the verification email and read the code or link from its body:
    {BASE_URL}/mail/pop?address=signup-7q2k9zx4m1@{MAIL_DOMAIN}&wait=20
  5. At the MFA enrolment screen, store the secret, then get the current code:
    {BASE_URL}/totp/set?key=run-7Q2K9ZX4M1&user=signup-7q2k9zx4m1&secret=JBSWY3DPEHPK3PXP
    {BASE_URL}/totp/get?key=run-7Q2K9ZX4M1&user=signup-7q2k9zx4m1
  6. Remember what you created so a teardown script can remove it:
    {BASE_URL}/lists/cleanup/push?key=run-7Q2K9ZX4M1&value=USER-1042

Try it out against the practice applications at testthis.now

The best way to learn these calls is to test something real. The applications hosted at testthis.now are practice targets for automated testing — sign-up journeys, email verification, multi-factor login, documents and integrations — so they are the natural place to put these endpoints to work.

Script a journey against one of them using mail/pop to catch its emails, totp to answer its MFA prompts, webhook to capture its callbacks and lists to share test accounts between virtual users. Or give your AI coding assistant the guide at {BASE_URL}/llms.txt and ask it to write the test for you.

Open by design — and for enterprises, your own copy

These endpoints are deliberately open: no sign-up, no API key, no login. That is what lets a test framework, a load-test script or an AI assistant use them with nothing but a URL. You are welcome to use them for learning, evaluation and your own test projects, within reasonable rate limits. Requests are throttled, so very heavy or sustained traffic — a large load test, for example — belongs in your own deployment.

For enterprise use, deploy it to your own cloud

An open service is the wrong place for an organisation's test data. For enterprise use we recommend running the whole stack in your own AWS account. Every endpoint then sits inside your environment and under your organisation's own policies and security model — for example your own authentication in front of the API, network restrictions, logging and monitoring, data residency and retention — and its capacity is sized for your test volumes.

How this service uses email

Email is one of the services, so here is exactly what it sends and receives.

  • Receiving. Mail sent to any address at {MAIL_DOMAIN} is stored so a test can read it back with mail/pop. Messages and their attachments are deleted automatically after 7 days.
  • Sending is for testing only. mail/send lets a test deliver a message into an application under test — for example to exercise an email-to-case or document-intake feature. Messages are sent from @{MAIL_DOMAIN} addresses only.
  • Recipients are restricted. The service will only send to addresses at {MAIL_DOMAIN} itself and to a short, fixed allow-list of test domains set by the operator. Any other recipient is refused before anything is sent, so it cannot be used to email the public.
  • No marketing, no lists. There are no mailing lists, subscriptions or bulk campaigns. Every message is a single, synthetic test message triggered by a test script.
  • Bounces and complaints. Because recipients are test domains under the operator's control, bounces and complaints are not expected. Amazon SES's account-level suppression list is enabled, so any address that bounces or complains is not sent to again.
  • Volumes are low. Typical use is a handful of messages per test run.

Acceptable use

Use synthetic data only. There is no authentication: anyone who knows or guesses a key or an email address on this domain can read what is stored under it. Never store real personal information, real passwords, or production data here.

Text messages: real texts are only accepted from registered capture handsets that hold the device key, and real sends only go to those handsets. Anyone who knows a handset's number can read its recent texts, so they are test SIMs only.

Requests are rate-limited (see open use). Stored data expires: received email after 7 days, captured webhooks after 30 days, uploaded import files after 90 days. Don't use the email service to contact anyone outside your own test environment.
